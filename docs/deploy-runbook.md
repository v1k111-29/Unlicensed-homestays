## 2. Neon database

1. Sign up at Neon (GitHub login is fine). Create a project `verified-stays`, region closest to
   Singapore (AWS `ap-southeast-1`) [A], latest PostgreSQL offered (16 or 17).
2. Create database `verified_stays` (or keep the default database and use its name below).
3. Copy the **direct** (not "pooled") connection string. It looks like
   `postgresql://<role>:<password>@<endpoint>.<region>.aws.neon.tech/verified_stays?sslmode=require`.
   Use the direct one: the login throttle uses transaction advisory locks and the backup uses
   `pg_dump` [A for pooler behaviour]. Keep `sslmode=require`.
4. Store the string in your password manager. It is a secret: never paste it into an issue,
   commit, chat, screenshot or the video.

## 3. Render web service

1. Sign up at Render with GitHub; allow access to `v1k111-29/Unlicensed-homestays` only.
2. Dashboard > **New > Blueprint** > pick the repository, branch `main` (after this branch is
   merged). Render reads `render.yaml`.
3. Render asks for the `sync: false` values:
   - `DATABASE_URL` = the Neon direct connection string (section 2).
   - `DJANGO_ALLOWED_HOSTS` = the service host name, e.g. `verified-stays.onrender.com`.
   - `DJANGO_CSRF_TRUSTED_ORIGINS` = the same host with scheme, e.g.
     `https://verified-stays.onrender.com`.
   If Render gives the service a different host name (name taken), correct both values under
   service > Environment and redeploy.
   `DJANGO_SECRET_KEY` is generated by Render (`generateValue`). Do not change it later: the
   audit log and the throttles store HMACs keyed by it (D58, D65).
4. Apply the Blueprint, then **Manual Deploy > Deploy latest commit** (`autoDeploy` is off).
5. Watch the deploy log: `Applying ...` migration lines (first deploy), the cache table, then
   Gunicorn `Booting worker`. Lines from the app are JSON.
6. Open `https://<host>/healthz`: expected `{"status": "ok"}`. Open `https://<host>/check/`.
7. Check the headers (PowerShell): `curl.exe -sI https://<host>/check/` should list
   `strict-transport-security`, `content-security-policy`, `x-frame-options: DENY`,
   `x-content-type-options: nosniff`, `referrer-policy: same-origin`. `http://` must redirect
   to `https://`.

## 4. Demo data and accounts (once, from your PC)

The free instance has no shell [A], so run these from the repository on Windows against Neon.
They only need `DATABASE_URL`; make sure your local `.env` has `DJANGO_DEBUG=1` (local
work), otherwise the production settings also ask for the host variables.

```powershell
# Session-only variable; nothing is written to disk or history in clear text.
$s = Read-Host "Neon direct connection string" -AsSecureString
$env:DATABASE_URL = [System.Net.NetworkCredential]::new('', $s).Password

# Migrations already ran at container start; running them again is a no-op.
.venv\Scripts\python.exe tasks.py migrate

# Synthetic DEV set only. The test set is reserved (rule 9) and is never needed in the demo.
# Run once: a second load of the same file is refused by the unique batch constraint.
.venv\Scripts\python.exe src\manage.py load_synthetic --set dev
```

Demo accounts: synthetic names only, never a real person (`create_account`, D61). One admin and
one officer per district you show (Nilgiris is the demo district, D18):

```powershell
$s = Read-Host "Password for demo_admin" -AsSecureString
$env:VS_NEW_PASSWORD = [System.Net.NetworkCredential]::new('', $s).Password
.venv\Scripts\python.exe src\manage.py create_account demo_admin --role admin --password-env VS_NEW_PASSWORD

$s = Read-Host "Password for demo_officer_nilgiris" -AsSecureString
$env:VS_NEW_PASSWORD = [System.Net.NetworkCredential]::new('', $s).Password
.venv\Scripts\python.exe src\manage.py create_account demo_officer_nilgiris --role officer --district Nilgiris --password-env VS_NEW_PASSWORD

Remove-Item Env:VS_NEW_PASSWORD, Env:DATABASE_URL
```

Passwords: long and unique, kept in your password manager; never shown in the video or the
note. If judges get a login, create a separate account for them and deactivate it afterwards.

## 5. Client address behind Render's proxy (Q27, Q41)

`render.yaml` sets `DJANGO_CLIENT_IP_HEADER=HTTP_X_FORWARDED_FOR` and
`DJANGO_TRUSTED_PROXY_HOPS=1` [A: Render's proxy appends the real client address as the last
`X-Forwarded-For` entry]. The address itself is never stored or logged (D58, D75). Check the
behaviour without looking at any address:

1. From your phone on mobile data, sign in 5 times with a wrong password for a made-up
   username: the 6th attempt shows "Please wait and try again" (address limit).
2. Within 15 minutes, from your PC on home Wi-Fi, sign in with a **different** made-up
   username and a wrong password once: it must show the normal error, not "Please wait".
   If it shows "Please wait", every client is being counted as one address (hops too low or
   the header wrong): try `DJANGO_TRUSTED_PROXY_HOPS=2`, redeploy, repeat.
3. Spoofed `X-Forwarded-For` prefixes are ignored by design (only the entry the trusted proxy
   appended counts); this is covered by `tests/test_m6_hardening.py`, not re-checked live.
4. Record the result in `docs/open-questions.md` Q41 and `docs/progress.md`.

## 6. Uptime monitor

1. Create a free UptimeRobot (or similar) account.
2. New HTTP(s) monitor: URL `https://<host>/healthz`, expect status 200, alert to your e-mail.
3. Interval [A]: Render sleeps after ~15 idle minutes, so an interval of **10 minutes** keeps
   it awake. Each ping also wakes Neon for ~5 minutes, so expect Neon compute about half the
   time, every day [E]. Check Neon's usage page after two days. If it would exceed the free
   allowance: point the monitor at `/livez` (keeps Render awake, lets Neon sleep; the first
   database query after sleep is slower [A]) or pause the monitor outside demo and judging
   windows.
4. Render's own health check uses `/livez` (no database) so it never keeps Neon awake (D81).

Before recording the video or a live demo: open `/healthz` and `/check/` once, then sign in,
so neither service is cold (R7).

## 8. CI deploy job (optional, disabled)

`ci.yml` has a `deploy` job that runs only on a push to `main`, after `checks` and `docker`
pass, **and** only when the repository variable `ENABLE_RENDER_DEPLOY` is `true`. To enable:

1. Render > service > Settings > **Deploy Hook**: copy the URL (it is a secret: anyone with it
   can trigger deploys).
2. GitHub > repository > Settings > Secrets and variables > Actions:
   - Secret `RENDER_DEPLOY_HOOK_URL` = the hook URL.
   - Variable `ENABLE_RENDER_DEPLOY` = `true`.
3. Keep Render's auto-deploy off so each commit deploys once, after CI passed.

To disable again, delete the variable (or set it to anything but `true`).

## 10. Logs and errors

- No Sentry (D84, cut order item 4). The app writes JSON lines to stdout (`config.logs`); IP
  and e-mail addresses, phone numbers, credentials in URLs and `password=`-style values are
  scrubbed, and request objects are never written. Gunicorn's access log is off.
- Render's dashboard shows these logs. Render's own edge/proxy may keep request logs with
  client addresses outside the app [A]; that is the host's data, not ours (Q42).
- A 500 shows Django's plain error page (`DEBUG=0`); the traceback is in the log, scrubbed.

## 11. Rollback

- Code: Render > service > Events/Deploys > roll back to the previous deploy [A].
- Migrations are not reversed by a rollback. M11 adds no migration. Before deploying a change
  with a migration, take a manual backup (`backup.yml` > Run workflow).
- Data: `docs/backup-restore.md` (restore into a new database, then switch `DATABASE_URL`).
